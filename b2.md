# dev_b2 — Beacons mesh, apps are clients

Decided 2026-11-27. Branch `dev_b2`, from `ccr-b899b983-3z4z08` (PR #1).

## The shape

```
  phone (Android)      desktop / Pi screen  console (backup)
  Slint                Slint                ratatui
     │ room engine (Rust, MLS keys stay on the device)
     └──────────────┬──────────────┬────────────┘
                    │ client link over Tor (onion, signed device key)
              ┌─────▼─────┐   mesh    ┌───────────┐
              │  Beacon A │◄─────────►│  Beacon B │   only Beacons mesh
              └───────────┘  (Tor)    └───────────┘
```

- **Keys on the device.** Every app (phone, desktop, console) keeps its MLS state and
  seals every frame; Beacons carry sealed frames only and cannot read rooms.
- **Only Beacons mesh.** A room's Beacons keep links to each other (today's mesh code,
  moved into the Beacon). A phone attaches to one Beacon it trusts (its own or a
  friend's, by scanning its code); no Beacon, no rooms.
- **Console mode.** `enigma-tui`: rooms, chat, invitations, and a large
  **Enable Beacon** button that runs a Beacon in the same process (a Pi or a desktop).
- **Android is a client only.** It never hosts an onion: Android kills background
  services and an always-on onion would drain the battery. The desktop app can enable
  Beacon like the console.

## Stages

1. **Split** — move mesh, mailbox and invitation-drop code out of the Tauri app into
   `beacon-node`; Beacon runs room meshes; build and tests green.
2. **Client link** — `enigma-client` + the Beacon side (phones attach, Beacon relays to
   its mesh and keeps frames for offline clients); signed device-key hello.
   **Done** (branch `b2-stage2`): PROTOCOL.md Part C, SECURITY.md "Stage b2: what a
   Beacon sees now". `beacon-node` gained `relay` (client links in, per-room Beacon
   mesh, offline queues, relayed redemptions), `proto`, `queue`, `link` (pluggable
   streams: Tor, TCP, in-process); `crates/enigma-client` implements
   `enigma_core::Transport` over the client link (Tor or in-process); the `beacon`
   binary serves links and HTTP on the same onion port (first-bytes sniffing) with a
   sealed `relay.sqlite`. The engine gained `admit_invited_via` (list the newcomer's
   Beacon at admission). The Tauri app still uses the app mesh until stage 5.
3. **Room engine in Rust** — port `rakotis/useChatChannel.ts` to `enigma-core`
   (tests ported too); the Vue app keeps its screens and calls Rust.
4. **Console app** — `enigma-tui` with rooms, chat, invites, Friends, Your Beacon, the
   lock gate and `:` commands (the Enable Beacon button was removed: client and Beacon are
   separate apps).
5. **Slint app** (decided 2026-11-27: Slint everywhere, TUI as backup) — `apps/enigma-slint`
   on `crates/enigma-app` + enigma-core + enigma-client, for desktop and Android (a client
   of Your Beacon everywhere; no Enable Beacon). The Tauri/Vue app is retired at parity.
   *Progress:* `crates/enigma-app` extracted from enigma-tui (Core state + actions,
   backend trait with DemoBackend / RealBackend stub, codes, letter avatars, EN/PL texts);
   enigma-tui runs on it. `apps/enigma-slint` (binary `enigma`): rooms + chat bubbles,
   room header with state line and ⋮ menu (Invite, Participants, Room info, Reset
   encryption, Leave, Delete), ☰ menu (New chat, Join chat, Friends, Settings), Friends
   (code, QR, check codes), Settings (nickname, language, Your Beacon card, Tor), Invite
   (QR + copy) (an Enable Beacon toggle existed here; removed in the parity round); light/dark from the
   system. `--demo` works end to end; without it, "not connected yet" until stage 2 wires
   RealBackend. Android: the cdylib with `android_main` cross-builds for aarch64 (NDK 27);
   APK packaging documented, not yet run. Headless UI tests and screenshots
   (`docs/screens/slint/`) use the software renderer.
   *Parity round (branch `b2-parity-3`):* RealBackend (vault, MLS store, enigma-client over
   Tor to Your Beacon, invitations via `admit_invited_via`), the lock gate (passphrase, PIN,
   idle lock, lock on hide, panic code, profiles, erase), offline mode, connection timeout,

6. **Docs, security, tests** — SECURITY.md (what a Beacon now sees: which client
   devices it serves, and per room which Beacons), PROTOCOL.md, real-Tor runs.

## What changes for privacy (to write up in stage 6)

- Your Beacon learns which rooms (by id) its clients are in and when they are online;
  it still cannot read anything. A friend's Beacon learns the same about you.
- Beacons of one room see each other's onions; phones' IP addresses are never seen
  by anyone (phones only dial out over Tor).

## Decision 2026-11-27 (later): Slint everywhere, then retire Tauri

Slint is the app for both the client and the Beacon, on desktop, Android and a Pi with
a screen; the TUI stays as the headless backup. The Tauri/Vue app is retired only
once the Slint app does everything it does (parity checklist in
`apps/enigma-slint/PARITY.md`). Android APK: `cargo apk build --lib` in
`apps/enigma-slint` (needs SDK platform 35, the NDK's newest; see its README).

## Decision 2026-11-27: Beacon is Linux only

Running a Beacon (the `beacon` binary, the `enigma-beacon` Slint app, and "Enable Beacon"
inside Enigma) is supported on Linux only: a Linux desktop or a Raspberry Pi. On Windows,
macOS, Android and iOS, Enigma is a client that attaches to a Beacon; the Enable Beacon
toggle is not shown there.

## Decision 2026-11-27: client and Beacon are separate apps

For now the client (Enigma, `apps/enigma-slint`, every platform) never runs a Beacon:
no "Enable Beacon" in the client. The Beacon is its own app (`apps/enigma-beacon`, Slint,
plus the headless `beacon` binary), Linux only. A Beacon is opaque: it carries sealed MLS
frames and never holds a room's keys, so it cannot read messages.

## Decision 2026-11-27 (latest): three Slint apps

- **Enigma27** (`apps/enigma27`, binary `enigma27`, Android `com.spectrumaipl.enigma27`):
  the client, Ubuntu and Android with equal priority. Never hosts a Beacon.
- **Pharos Lighthouse** (`apps/pharos-lighthouse`, binary `pharos-lighthouse`): the Beacon
  app. *Lighthouse is the Beacon app*: the UI says "Lighthouse"; the protocol and the
  server concept stay "Beacon" in the docs. Linux only (desktop, Raspberry Pi).
- **Enigma27 Combo** (`apps/enigma27-combo`, binary `enigma27-combo`): both in one window
  (left nav: Chats / Friends / Settings, then Lighthouse: Overview / Clients / Rooms /
  Settings / Log). The Lighthouse runs in-process (beacon-node Relay, sealed SQLite
  queue, its own onion via pharos-tor) and the combo's own client attaches through
  `enigma_client::in_process` (no Tor hop to itself); friends reach it over Tor. Stopping
  the Lighthouse keeps the client's data ("Your Lighthouse is off", still readable).
  Linux only. Both apps' code is reused as libraries (the combo's .slint imports their
  ui folders).

Renames: `apps/enigma-slint` → `apps/enigma27`, `apps/enigma-beacon` →
`apps/pharos-lighthouse` (screens in `docs/screens/enigma27/`, `docs/screens/lighthouse/`,
`docs/screens/combo/`). Build: `./build.sh enigma27 | lighthouse | combo` (release + .deb).
